# EnjoySync 0.1 架构

## 生命周期与线程

应用初始化 AOO 全局环境，然后建立 AudioEngine、原生播放输出、Transport、系统采集后端与 GUI。关闭窗口仅隐藏界面；退出时先停止采集，再发送 BYE、关闭传输、保存设备记录并销毁 AOO。

GUI / 控制线程负责设置、设备列表、采集启停和原子配置保存；隐藏窗口不刷新电平表。系统采集回调将双声道 float 数据交给 AOO source。播放回调处理固定数量的 AOO sinks，平滑应用各路音量后进行混音限幅。缓冲预分配，回调不会等待生命周期锁；重配置冲突时该块输出静音。

macOS 菜单栏右键菜单推迟到主 RunLoop 的 default mode 打开，菜单退出同样等待原生事件跟踪结束后执行。不能在状态栏按钮的 mouseDown 内同步弹出菜单，也不能只用 JUCE `callAsync`：它在 event-tracking mode 中也会执行，嵌套菜单可能消耗外层按钮等待的 mouseUp，阻止主事件循环及时退出。延迟打开时使用组件安全指针处理退出前的销毁。日志记录菜单退出请求、清理开始和清理完成耗时，便于区分事件循环等待与资源释放。

Transport 的网络线程独占所有 DTLS 上下文、网络会话和设备记录。GUI 通过命令队列修改，读取快照。地址解析在线程中执行，完成结果带 generation，主动断开或新请求后忽略旧结果。

AOO setup 不是线程安全接口，重配置使用独占生命周期锁；网络处理使用共享锁；实时回调尝试共享锁且不阻塞。每个播放 sink 在 AudioEngine 生命周期内保持有效，防止移除设备时产生回调悬空指针。

## 网络与身份

两个非阻塞 UDP socket 分别监听 IPv4 和 IPv6 的同一端口，IPv6 使用 V6ONLY。绑定失败明确报错，不静默改用随机端口。不使用 AOO 的发现服务器或内部网络客户端。

DTLS 1.2 的 PSK 为每次首次启动生成的 32 位十六进制邀请密钥，密码套件限定 AES-128-GCM-SHA256。Mbed TLS 提供认证、加密、重放保护、握手重传和 cookie 验证；应用不自行实现密码算法。密钥持有者能够进行配对；这是一种设备邀请模型，不是账户或 PKI 身份模型。

应用数据首字节区分控制（1）和 AOO（2）。控制内容是限定长度的 JSON，音频使用 AOO 原始数据包。媒体包为 1000 字节上限，DTLS MTU 为 1200 字节。任何 AOO 数据只有通过已认证、绑定到当前设备会话的 DTLS 通道才能进入解码器。

HELLO 包含协议版本、稳定设备 UUID、名称、接收 sink ID、接收偏好、共享状态和返回邀请密钥。返回密钥仅在 DTLS 加密通道内发送，使双方都可以保存和恢复连接。已保存地址对应的 UUID 改变时停止自动重连，要求显式重新配对。

同一规范化主机 / 端口的并发请求复用原记录；握手后按稳定 UUID 合并 IP / 域名别名。同一端点双方同时拨号时，比较标准 DTLS ClientHello 的公开随机数，使双方确定性地保留同一个发起方向。认证后出现多地址会话时再按稳定设备 UUID 去重。同一端点重新握手时，新旧上下文可能暂时共存；加密应用记录交给该端点所有已完成握手的上下文验证，错误密钥及重放包由 Mbed TLS 丢弃。握手记录及 ChangeCipherSpec 优先进入待握手的上下文；应用记录不进入尚未完成的握手，避免旧媒体触发 Finished 阶段的 MAC 错误，过早到达的 HELLO 由对端周期重发。只有已认证且设备身份匹配的 HELLO 才替换旧会话，不等待旧会话心跳超时；多地址会话仍按稳定 UUID 仲裁。

UDP 发送缓冲临时不足、非阻塞暂不可写或系统调用被中断，按丢失一个数据报处理并计数，不作为 DTLS 致命错误，也不遗留需要用相同参数重试的 TLS 写入。握手依靠 DTLS 重传，控制消息周期重发，媒体依靠 AOO 恢复。其他发送错误停止使用该上下文，下一轮网络循环统一清理会话，避免在 AOO 共享生命周期锁内执行重入的音频配置。Windows 关闭共享 UDP socket 的 ICMP connection-reset 报告。

## 状态与恢复

设备状态包括离线、解析、连接、安全连接成功、退避重试、错误。连接与音频静音独立。HELLO 每秒重复一次同步控制偏好；PING / PONG 每秒测量往返时间；任何已认证数据都刷新生存时间，5 秒未收到数据后失联。

正常退出使用加密 BYE 和 DTLS close-notify。主动断开的 BYE 带 manual 原因，双方停止本次运行中的重连。主动断开的一方拒绝对方后台重试，直到本机用户再次连接；收到通知的一方仍允许对方主动恢复。历史记录与下次启动的 autoConnect 偏好保留。已认证的连接双方均可恢复本次连接，不依赖哪一方最初拨号。已建立会话失联后，先等待 250–500 ms，直接尝试最近成功的地址一次；失败后重新解析 DNS 并继续指数退避。首次连接失败仍使用 1、2、4、8、16、32 秒退避和少量随机扰动，每个地址握手预算约 3 秒。

默认在配置目录的 `logs/transport.log` 中记录连接状态变化、读写 / 握手错误码、心跳超时前的收包间隔、UDP 发送丢弃及错误计数、DTLS 队列丢弃计数和超过 250 ms 的网络线程循环间隔。每 30 秒记录累计媒体包计数和采集结果。日志不记录密钥、控制消息正文或音频；启动时截取旧日志最后约 512 KiB，`ENJOYSYNC_TRACE=1` 同时输出到标准错误。

## 音频与路由

每台设备有一个系统声音 source，每个对端有一个独立 sink。source 向允许共享且正在订阅的对端发送；sink 独立接收、静音和混音。采集排除本应用渲染音频，因此远端声音不会自动回传。

采集使用系统实际采样率；传输为 48 kHz / 双声道 / 10 ms，AOO 负责重采样和重分块。默认最低抖动缓冲 30 ms。欠载事件触发缓冲递增，稳定 30 秒后逐步回到用户最低值，上限 200 ms。此策略是初版启发式算法，需要在真实网络和设备上调参。

macOS 使用私有全局 Core Audio Tap，保持被采集应用原始播放不变。Windows 使用 Process Loopback，排除本进程树，采集范围跨系统输出端点。接收端播放输出独立选择，通过 JUCE 音频设备管理器创建。
