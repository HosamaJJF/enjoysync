## 2026-10-14 有线局域网传输排查

- 用户反馈 Mac → Windows 有线局域网音频偶发断连，设备状态进入重连，约 10 秒恢复。原版本没有默认落盘的断线诊断，因此尚不能确定现场首次断连的触发原因。
- 新增快速同端口重启回归，在修复前稳定失败：对方重新握手后，新应用数据仍被路由到旧 DTLS 上下文；新上下文无法获得认证 HELLO。旧的设备 ID 仲裁也可能保留已失效的同端点会话，延长恢复时间。修复后只有身份匹配的认证 HELLO 才替换旧会话，恢复不再等待旧心跳期限。
- 静态检查发现非阻塞 UDP 的暂不可写、发送缓冲不足及调用中断被统一转换为 DTLS 致命发送错误。现在按数据报丢失处理并计数；其他发送错误及时关闭上下文并重连。Windows 关闭共享 UDP socket 的 ICMP connection-reset 报告。临时原生发送错误尚未在真机上主动注入验证。
- 已建立会话断线后，两端均可在 250–500 ms 后尝试最近成功的地址一次，失败后重新解析并继续退避；保留 5 秒无认证数据的故障检测期限。此等待值不等同于总断音时长。
- 使用真实 UDP 中继和合成音频验证每 13 包丢弃一包、1.2 秒双向中断和超过 5 秒的单向中断。零散丢包及短中断没有触发重连；最终单向故障测试在路径恢复后约 410 ms 重新连上，并验证音频恢复。
- 最终 macOS Release 编译通过，`ctest --test-dir build-release --output-on-failure` 1/1 通过，耗时 33.03 秒；额外 8 轮同时拨号及保存设备启动恢复回归全部通过。应用 ad-hoc 签名和 `codesign --verify --deep --strict` 通过。测试监听端口改为先探测可用端口，避免与本机临时 UDP 端口竞争。
- 默认增加 `logs/transport.log`，记录断线错误码、入站数据间隔、UDP / 队列丢弃计数和网络线程停顿；不记录密钥或音频。Windows 新构建及 Mac → Windows 真机至少 30 分钟持续共享仍待验证，现场复现时应对照两端相同时段日志。

## 2026-10-14 CI 音频测试时序修复

- 提交 `687704e` 的 Windows 编译、完整回归和便携版打包通过；macOS 编译通过，但首次 Opus 输出断言失败。失败时已完成 DTLS 配对并收发 131 个媒体包，输出为零，日志包含额外发送缓冲溢出。
- 排查发现测试音频线程使用墙钟时间戳并在调度延迟后突发补跑过期回调。注入 700 ms 启动延迟可复现额外溢出，新增的禁止突发补跑断言在旧实现上失败。改为每个 10 ms 音频块推进模拟采样时钟，错过调度时重新安排下一次回调；首次输出改为在 4 秒期限内等待实际解码幅值，不再固定睡眠 1.3 秒后取样。
- 新增 1.7 秒启动延迟和每 8 块停顿 80 ms 的真实 UDP / DTLS / Opus 回归，要求解码输出大于 0.02 且没有突发补跑回调；可用 `enjoysync_tests --audio-startup` 单独运行。修复后两项通过，本机 Release 编译及完整集成测试 1/1 通过，耗时 34.62 秒。
- CI 开启已有的 `ENJOYSYNC_TRACE`，失败日志可包含连接与网络线程停顿信息，不记录密钥或音频。此次修改限于测试、CI 和验证记录；两平台新 CI 结果仍需以实际运行记录为准。
- 提交 `b0a1133` 的 macOS 延迟回归已输出约 0.1605 的幅值，但新增的禁止补跑断言发现，绝对截止时间调度仍会在晚唤醒后压缩相邻回调间隔。进一步改为每次回调完成后相对等待 10 ms，保持独立模拟采样时间戳，消除部分追赶调度；本机完整回归再次 1/1 通过，耗时 34.91 秒。
